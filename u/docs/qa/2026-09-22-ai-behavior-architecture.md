# Чому AI дає неточні факти, зайві питання та нечіткі наступні кроки

22 вересня 2026. Аналіз локального коду й збереженої симуляції від 21 вересня. Продуктовий код, модель, налаштування та production-дані не змінювалися.

## Поточна схема

`AiAgentService.chat` збирає locked core + редаговану рольову інструкцію, 12 останніх повідомлень, working state, збережену чернетку та словник фільтрів. Одна модель вирішує, що запитати, які інструменти викликати, який рекламний текст написати та як описати наступний крок. Інструменти виконують перевірки власника, ревізії, параметрів і структури даних. Після завершення tool loop текст відповіді очищується як HTML та повертається клієнту.

Паралельно UI сам визначає прогрес Brief/Pages/Content і доступність checkout. Прямий підбір із кнопок уже обходить модель. Це добра основа: ціни та пакети можна отримати детерміновано, записи обмежені чернетками, а клієнтська оплата відокремлена.

## Чотири механізми проблем

### 1. Правдивість каталогу перевіряється, правдивість рекламного тексту — ні

- `agent-prompt.service.ts:17`: заборона вигадувати influencers, prices, statistics, ids не описує окремо факти про реліз.
- `add-campaign-content.tool.ts:82`: валідація перевіряє довжини й кількість значень. Далі текст моделі записується в кампанію.
- У CampaignBrief немає окремого releaseStatus; dateRequest позначає дату релізу, вікно кампанії або Flexible. contentAvailability описує готовність матеріалів, а не публікацію треку.
- `ai-agent.service.ts:193` повертає збережений рекламний текст у наступний контекст без джерела кожного факту. Отже, згенероване раніше твердження може знову потрапляти до моделі як частина кампанії. Це структурний ризик; подальше закріплення конкретної вигадки в тривалому діалозі окремо не відтворювали.

Мінімум: явно заборонити домислювати реліз, назви, дати, досягнення; за невідомого статусу використовувати нейтральний текст. Системніше: розділити підтверджені відомості, рекомендації AI та згенерований контент. Невідомий статус має залишатися unknown, доки є джерело. Поле `confirmed:true`, самостійно заповнене моделлю, не є доказом підтвердження клієнтом.

### 2. Стан кампанії та текст «що далі» визначаються різними місцями

- `finalize-campaign-draft.tool.ts:97` лише переводить чернетку до strategyTable, а результат інструмента каже Ready for review. Інструмент не запускає рекламу й не бере оплату.
- `ai-campaign-draft-card.tsx:1032` відкриває checkout окремою кнопкою.
- `ai-agent.service.ts:466` приймає вільний текст моделі як фінальну відповідь; `:592` виконує HTML-очищення, а не перевірку відповідності наступного кроку реальному стану.
- `pagesReady` від інструмента означає наявність хоча б одного publishing detail; це не перевірка правдивості тексту чи готовності кампанії до запуску.
- Working state має contentAdded/finalized, але немає окремого об'єкта «яку саме дію зараз запропоновано підтвердити». Відповідність «так» останньому питанню покладена на prompt і історію.

Мінімум: точна термінологія «чернетка», «перегляд», «оплата», «запуск» та реальний nextAction у результатах інструментів. Уточнити значення ready для моделі. Системніше: сервер готує компактний опис допустимих наступних дій; UI й AI спираються на нього. Для конкретної очікуваної заміни пакета можна зберігати pendingAction з її параметрами й ревізією. Це не потребує підтверджувати кожне збереження чернетки.

Користувач раніше просив залишити правила readiness і пам'ять. Тут описано причину та можливий напрям, а не виконано їхню зміну. Невеликий адаптер для назви наступного кроку можна зробити, не змінюючи самих бізнес-умов readiness.

### 3. Частина зайвих питань прямо наказана кодом

- Locked core `agent-prompt.service.ts:23` зобов'язує запросити все в одному пакеті й запитати shared чи per-page.
- Опис `add_campaign_content` повторює «First ask whether … one shared post or tailored content».
- Загальна інструкція радить вибрати default при делегуванні, але локальна вказівка знову вимагає питання.
- Prompt одночасно просить показувати total/remaining після пошуку й «never narrate saves or repeat values» після запису. Такі широкі формулювання залишають моделі розв'язувати, що саме слід повторити.

Рішення: одна узгоджена політика питань. Критичний невідомий факт уточнюємо лише коли він потрібен; делеговане рішення вирішуємо рекомендацією; необов'язкове відкладаємо. Shared copy можна пропонувати за замовчуванням, якщо це відповідає запиту, з можливістю редагування. Прибрати обов'язкове питання одночасно з core і опису tool, а не додавати протилежне правило в кінець prompt.

### 4. Назви результатів обіцяють більше за алгоритм

- `search-accounts.tool.ts:74`: greedy packing, який не гарантує оптимального рішення.
- Ті ж результати названі `best_value` і `max_reach` (`:423`).
- У результаті є `reach`, рівний summed followers; сумісний alias передається й моделі через `searchResultForModel`.
- Модель бачить цифри й сильні назви, але не отримує структурованого пояснення меж алгоритму та відомих обмежень метрик.

Рішення без зміни ранжування: повертати нейтральну назву, точну основу підбору (наприклад, співвідношення аудиторії до ціни з урахуванням обраних країн), обмеження й reasonCodes. Не передавати моделі followers під назвою reach. Формулювання «рекомендований пакет» допустиме; «доведено найкращий» — лише за відповідного доказу. Не виводити прогноз прослуховувань зі самої кількості підписників.

## Пропонована послідовність

1. Узгодити core, рольову інструкцію й описи інструментів; додати короткі приклади бажаних відповідей для чотирьох поточних помилок. Зберегти наявний вільний діалог.
2. Додати до відповідей інструментів невеликий контракт: фактичний стан, виконана дія, допустимий наступний крок, відомі обмеження рекомендації. Сервер задає зміст кнопки/дії; модель пояснює його природною мовою.
3. Відділити джерела фактів від згенерованої копії. Для невідомих фактів — нейтральний текст, а не нова обов'язкова анкета.
4. Додати перевірки саме змісту до наявних тестових сценаріїв: unknown release не стає «вже вийшов»; після делегування немає нового меню зайвих рішень; review не називається launch; heuristic не називається математичним максимумом. Перевіряти і reply, і збережений content. Окрема платформа аналітики не потрібна.

Структуровані поля обмежують варіанти переходів і полегшують валідацію, але самі по собі не гарантують правдивості вільного тексту. Семантичні перевірки мають враховувати факти й джерела; ще одна модель-рецензент може допомагати, але теж помиляється. Вона не є необхідною першою зміною.

## Межі попередньої перевірки

У `simulate-lazy-client.ts:205` репозиторій prompt повертає null, тому симуляція використовує default-role prompt. Справжня модель була live, але каталог і записи — синтетичними. Активний prompt із адмінки production не читався; він може відрізнятися від default. Його треба порівнювати з випробуваною версією перед твердженнями про точну поведінку розгорнутого продукту.

Prompt-тести переважно перевіряють наявність потрібних рядків. `content_saved` у симуляції перевіряє наявність контенту. Тому вони закономірно пропустили «трек уже доступний». Для цього висновку нові платні запуски моделі не виконувалися; використано наявний запис реального діалогу й поточний код.
