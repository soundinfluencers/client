# Правила работы Codex

Эти инструкции применяются ко всему репозиторию. Учитывайте более узкие `AGENTS.md`, существующие соглашения проекта и актуальное задание пользователя. Рабочая ветка Codex — `codex-main`; изменение `main`, merge и force-push не входят в обычное разрешение на разработку.

## Обязательная цепочка подагентов

Координатор создаёт отдельных подагентов с ролями **программист**, **тестер**, **ревьюер** и **документатор**. Он управляет передачей результатов, но не подменяет независимую проверку собственной оценкой. Автор реализации не утверждает её как тестер или ревьюер. Ревьюер может повторно использоваться для финальной проверки документации; документатор не утверждает собственные документы.

Если среда не поддерживает создание подагентов, сообщите об этом как о блокировке обязательной проверки. Не изображайте несколько агентов последовательными сообщениями одного агента, не заявляйте о прохождении этапов и не публикуйте релиз до устранения блокировки или явного изменения пользователем требования.

Порядок для каждой задачи:

1. **Координатор** фиксирует цель, критерии приёмки, затронутые репозитории и допустимые действия. Читает инструкции, зависимости и команды проекта. Выдаёт каждому агенту ограниченную область работы; одновременное редактирование одних файлов запрещено.
2. **Программист** реализует изменение, выполняет доступные предварительные проверки и передаёт тестеру diff, идентификатор проверяемой версии, критерии приёмки и известные ограничения. Он не запускает деплой.
3. **Тестер** независимо проверяет поведение и регрессии, граничные и ошибочные случаи, выбирает соразмерные проверки. При дефекте передаёт программисту воспроизведение, ожидаемый и фактический результат. После исправлений снова проверяет новую версию. Только успешный результат передаётся ревьюеру.
4. **Ревьюер кода** проверяет корректность, безопасность, совместимость контрактов, архитектуру и достаточность проверок. Блокирующие замечания возвращает программисту. Любое исправление кода снова проходит тестера и ревьюера; прямой переход от исправления к документатору запрещён.
5. **Документатор** после положительного code review обновляет существующие документы либо создаёт необходимые новые. Описывает фактическое поведение, конфигурацию, способы проверки и эксплуатационные изменения. Не дублирует документацию без причины. Если пользовательские или эксплуатационные документы менять не требуется, фиксирует конкретное обоснование.
6. **Ревьюер документации** сверяет документы с одобренным кодом, проверками и реальными путями и командами. Ошибки только в документах возвращает документатору с повторным review. Если требуется изменение кода, возвращает программисту и заново запускает цепочку тестер → ревьюер кода → документатор → ревьюер документации.
7. **Координатор** сверяет итоговую версию с проверенной, подтверждает отсутствие незакрытых блокеров и сообщает пользователю результат. Успешная цепочка означает готовность к публикации, но сама по себе не разрешает деплой.

## Доказательства проверок и готовности

Передачи между агентами содержат: роль и исполнителя, критерии приёмки, точную версию (commit SHA или идентификатор снимка содержимого/tree), область проверки, вывод `PASS`, `FAIL` или `BLOCKED`, замечания и ссылки на файлы. Тестер указывает выполненные команды и результаты; ревьюер — проверенный diff и незакрытые риски. Для невыполненных проверок обязательны причина и последствия. Недоступная зависимость или credentials означают `BLOCKED`, а не `PASS`.

Сохраняйте краткую запись этапов в описании PR, отчёте задачи или согласованном журнале. Не выдавайте запланированную проверку за выполненную. Не меняйте тесты, lint, типизацию или CI только ради зелёного статуса; baseline-проблемы отделяйте от новых дефектов. Новые тесты должны проверять значимое поведение, а не повторять реализацию; для исправления ошибки предпочтителен регрессионный тест. Для простого изменения документации не запускайте весь runtime без необходимости — тестер проверяет содержание и применимые проверки документации.

Одобрения относятся только к указанному содержимому. Изменения кода, зависимостей, конфигурации или workflows аннулируют затронутые проверки и требуют повторных тестирования, code review и актуализации документации. Правка только текста документации требует повторного review документации; инструкции, влияющие на сборку, запуск, безопасность или деплой, дополнительно проверяются тестером. Перед публикацией убедитесь, что новых непроверенных изменений нет.

## Публикация и деплой

- Не подключайтесь к VPS и не выполняйте удалённые команды: SSH, SCP, rsync, remote shell и обходные каналы не разрешены для обычной работы Codex. Подготовьте изменения в GitHub и инструкции владельцу сервера; серверные действия выполняет владелец или заранее настроенная автоматизация.
- Перед любым push проверьте активные workflows и другие известные триггеры целевой ветки. Push, merge, tag или вызов workflow, запускающий выкладку, считается деплоем. Если наличие автодеплоя невозможно установить, не предполагайте его отсутствие.
- Для деплоя требуется явное разрешение пользователя на конкретный проверенный набор изменений, целевую ветку и инстанс. Нельзя выводить такое разрешение из просьбы исправить код или из успешного review. Действующее разрешение на тот же набор и инстанс повторно не запрашивается. Явно согласованное постоянное правило автодеплоя для конкретной ветки и инстанса также допустимо в оговорённых пределах. Новые изменения вне этих пределов или другой инстанс требуют отдельного разрешения. Изменения только Markdown тоже могут запускать деплой.
- Публикация в ветку без деплоя допускается в пределах задания пользователя после обязательной цепочки проверок. Не меняйте workflows, права доступа, secrets, правила защиты или deployment triggers, чтобы обойти ограничения. Не запускайте production build/publish/deploy workflow вручную без соответствующего разрешения.
- Deploy workflow должен проверять источник сборки, разрешённую ветку, точный SHA и образ; использовать защищённые credentials, последовательное выполнение релизов одного инстанса, health checks и проверенный rollback. Не передавайте серверу произвольные команды из рабочего кода. Не храните ключи, пароли и реальные `.env` в Git, документах или логах.
- Миграции БД и другие необратимые операции не являются частью обычного автодеплоя. Для них нужны отдельное разрешение, план backup/restore и проверка совместимости отката. Откат образа не откатывает данные.

`AGENTS.md` задаёт поведение агента, но не создаёт технической защиты GitHub. Независимые проверки, права записи, защищённые deployment workflows, environments и разрешения на релиз должны дополнительно обеспечиваться настройками платформы и CI. Не заявляйте, что агентская проверка равна обязательному GitHub approval или что эти ограничения уже настроены, без фактической проверки.

## Качество кода

- Следуйте практикам установленной версии фреймворка и существующей архитектуре проекта. Уточняйте версию по manifests/lockfiles; при необходимости сверяйтесь с официальной документацией для этой версии. Не обновляйте major версии и не внедряйте новый стек без требования задачи.
- Поддерживайте **low coupling / high cohesion**: тесно связанные действия объединяйте в одном модуле, зависимости между модулями делайте явными и минимальными. Соблюдайте **Single Responsibility Principle** — у компонента, сервиса или функции должна быть одна понятная ответственность. Не создавайте циклических зависимостей, скрытых глобальных состояний и универсальных объектов на все случаи.
- Используйте ясные доменные имена, небольшие связные функции, явные контракты и понятную обработку ошибок. Устраняйте значимое дублирование без преждевременных абстракций. Предпочитайте простое решение, достаточное для задачи; не устраивайте несвязанный рефакторинг.
- Сохраняйте типобезопасность. Не вводите необоснованные `any`, подавления ошибок типов/lint или молчаливые `catch`. Проверяйте входные данные на границах, не раскрывайте secrets и персональные данные в ошибках или логах.
- Отступы, табуляцию, пробелы, кавычки и переносы определяет существующая конфигурация formatter/linter/editorconfig; при её отсутствии следуйте ближайшему коду. Не смешивайте стили, не переформатируйте посторонние файлы. Читаемость и соответствие проекту важнее искусственной имитации авторского почерка.
- Добавляйте комментарии к нетривиальным решениям, ограничениям, инвариантам и обходам: объясняйте **почему**, а не пересказывайте каждую строку. Публичные контракты документируйте по принятому в проекте стилю. Не оставляйте устаревшие комментарии, закомментированный код и бессрочные TODO без контекста.
- Проверки подбирайте по изменению: форматирование, lint, типизация, build, модульные/интеграционные/UI тесты согласно реально существующим scripts. Не выдумывайте отсутствующие команды и не добавляйте framework только ради соблюдения списка. Сообщайте о непроверенных областях прямо.

## Практики client: React и TypeScript

Приложение находится в `u/`: React 19, TypeScript 5.9, Vite 7, TanStack Query 5, React Hook Form и Zod 4. Текущий container workflow использует Node.js 22. Все npm-команды ниже выполняются из `u/`; версии уточняйте по его manifests и lockfile.

- Пишите функциональные компоненты и связные custom hooks с одной ответственностью. Соблюдайте Rules of Hooks, не вызывайте hooks условно. Effects используйте для синхронизации с внешними системами, с корректными зависимостями и cleanup; производные значения вычисляйте без лишнего состояния.
- Соблюдайте существующие границы модулей. Server state и cache ведите через принятый TanStack Query слой; transient UI state держите локально, форму — в React Hook Form/Zod. В проекте есть Redux и Zustand: не дублируйте одно состояние в обоих и не смешивайте stores без архитектурной необходимости.
- Для изменённых сценариев проверяйте loading/error/empty/success, валидацию форм, повторную отправку и доступ с клавиатуры. Используйте семантическую разметку, labels, видимый focus и адаптивную вёрстку.
- Не вставляйте недоверенный HTML без надёжной санитаризации. Не храните серверные secrets в frontend env; значения, попадающие в bundle, доступны пользователю. UI не является границей авторизации.

Для runtime-изменений выполните в `u/`: `npm ci`, `npm run lint`, `./node_modules/.bin/tsc -b`, `npm run build`. Текущий `build` выполняет только `vite build` и не заменяет отдельную проверку типов. Форматирование следует существующему ESLint и стилю соседних файлов; новый formatter не добавляйте без отдельной необходимости.

Сейчас script `test` отсутствует: не заявляйте о запуске `npm test`. Тестер проверяет затронутые UI-потоки и ошибки в безопасном тестовом окружении с конкретными шагами и результатами; если оно недоступно, фиксирует блокировку. Новую инфраструктуру автоматизированных тестов согласуйте отдельно, не объявляйте её существующей.
